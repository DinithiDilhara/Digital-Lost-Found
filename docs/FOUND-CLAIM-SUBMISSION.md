# Found-item claim submission (Nipuni)

This feature lets a signed-in student tell the owner of an open lost report that
they found the item. It is separate from the existing local **Preview Demo Claim**
on found-item reports. It creates a real MySQL claim; it does not send notifications,
accept/reject claims, or mark reports as returned.

## Setup and running

From `D:\Projects\Digital-Lost-Found`, with MySQL running and the existing root
`.env` configured, apply the additive migrations:

```powershell
.\scripts\Initialize-Database.ps1
```

The initializer now includes `database/migrations/003_found_claims.sql` after 001
and 002. It uses `CREATE TABLE IF NOT EXISTS` and can be rerun. No existing data is
deleted or reseeded. A MySQL account with CREATE/ALTER privileges is needed for
initialization. Restart the backend after building the new code.

```powershell

```

Run the frontend in another terminal:

```powershell

```

Open `http://127.0.0.1:5173/`. Keep both terminals running. These separate commands
avoid starting a second backend through the combined `npm run dev` command.

The database readiness check at `/api/health/db` now verifies `found_claims` too.

## API contract for Suwani and Dinithi

`POST /api/lost-items/{numericLostItemId}/claims`

Use the existing session cookie, `Content-Type: application/json` and
`X-DLF-Request: 1`. React calls `api.submitFoundClaim('lost-10', values)`, which
converts the typed UI ID into the numeric lost-item route and includes credentials.

Request:

```json
{
  "foundLocation": "Engineering Library, desk near the entrance",
  "message": "I found the calculator beside the reference books."
}
```

Both fields are trimmed, required and validated on the server. Limits are 150
characters for location and 1,500 for message. The client cannot choose the finder,
owner or claim status. The finder comes from the authenticated session; the owner
comes from the lost report. Successful creation returns HTTP **201**, for example:

```json
{
  "claimId": 1,
  "itemId": 10,
  "finderId": 2,
  "ownerId": 1,
  "status": "PENDING"
}
```

These are example IDs; actual responses contain database-generated/retrieved IDs.
The API helper returns this complete object, and `FoundClaimModal.onSubmitted`
receives it. Suwani can use `claimId` and `ownerId` for future notification
integration. For reliable delivery, a future server-side notification integration
should originate from the committed claim, rather than trusting client-supplied
recipient IDs. No notification module or placeholder notification is added here.

Errors have the existing shape `{ "error": "Human-readable message" }`:

| HTTP status | Meaning |
| --- | --- |
| 400 | Invalid JSON, invalid field type/length/blank value, or out-of-range ID |
| 401 | Missing or expired login session |
| 403 | Self-claim, or missing required request header |
| 404 | Lost report does not exist, or route does not match |
| 405 | A method other than POST is used on the claim route |
| 409 | Report is no longer open, or this finder has already submitted a claim |
| 415 | Request does not use JSON content type |
| 503 | Database/service failure, using the existing error handler |

Only lost reports with `LOST` or legacy `OPEN` status are eligible (case-insensitive).
`RETURNED`, `RESOLVED`, legacy lost-item `FOUND`, `CLOSED` and all other values are
rejected. Submitting a claim never changes the report's status.

## Database contract

| Column | Type / meaning |
| --- | --- |
| claim_id | BIGINT UNSIGNED, generated primary key |
| lost_item_id | INT, required foreign key to lost_items.item_id |
| finder_id | INT, required foreign key to users.user_id |
| found_location | VARCHAR(150), required nonblank text |
| message | VARCHAR(1500), required nonblank text |
| status | VARCHAR(30), required, default PENDING |
| created_at | TIMESTAMP(6), generated by MySQL |

The unique key `(lost_item_id, finder_id)` permits one claim per student per lost
report, regardless of future claim status. Separate finders may each submit a
claim. Indexes support finder history and status/time queries. Ownership can be
retrieved by joining `lost_items.user_id`; it is not duplicated in this table.

The repository locks the lost report with `SELECT ... FOR UPDATE`, checks its
owner/status, inserts the claim and commits in one transaction. Report updates
and deletion serialize against that lock, and the unique key protects against
concurrent duplicate submissions. Failed requests roll back. There is no cascading
deletion: deleting a report/user with claims is rejected, preserving the claim
history for future verification. Existing unrelated report deletion is unchanged.

Dinithi can use `claim_id` and the stored `PENDING` status for future verification.
Status remains a VARCHAR rather than an enum so the team can agree on future
states without this feature guessing their names. This module has no status-update,
acceptance/rejection, claim-listing or return endpoint.

## UI behavior

Only an authenticated non-owner viewing an open **lost** report sees **I Found
This Item**. The existing dialog, fields, buttons and green/cream styles are reused.
The dialog displays read-only item name/category/lost location and two required
inputs. It shows validation/API errors, disables inputs while submitting, prevents
double submission, and keeps the dialog open on failure. Closing is blocked only
while the request is in flight. Success closes the form, disables the action for
that item/account for the current view, and displays the requested success text.

Claims are never stored in localStorage. After a full reload the button can appear
again; submitting again returns a clear duplicate error from MySQL. A future claim
history/status view can expose persisted status without extending this submission
module into the teammates' verification work.

## Automated tests

```powershell
. .\scripts\Use-DevTools.ps1
mvn -B -ntp "-Dmaven.repo.local=$projectRoot/.local/m2" -f backend/pom.xml package
npm test
npm run build
```

Real integration tests create test accounts/reports and retain them for inspection.
Always use a separate database. Place its DB_URL/DB_USER/DB_PASSWORD in an ignored
file such as `.local/claims-test.env`, then run:

```powershell
.\scripts\Initialize-Database.ps1 -ConfigFile .local/claims-test.env
$env:DLF_ENV_FILE = '.local/claims-test.env'
npm run test:integration
```

The harness starts/stops its own Java process on port 15000 and refuses an occupied
port. Set `DLF_TEST_PORT` if necessary. It never stops the normal backend.
`tests/found-claims.mjs` adds claim authorization, validation, status, concurrent
duplicates and persistence checks to the existing report/auth/messaging suite.
Results are written to ignored `.local/integration-results.json`.
